# YOLOv8s с дополнительным уровнем P2

Конфиг `configs/yolov8/yolov8_s_p2_syncbn_fast_8xb16-500e_coco.py`
наследуется от `yolov8_s_syncbn_fast_8xb16-500e_coco.py` и добавляет
четвёртый масштаб детекции с шагом 4. Новых классов модели не требуется:
существующие backbone, YOLOv8PAFPN и голова поддерживают четыре уровня.

## Архитектура

| Уровень | Шаг | Размер при входе 640x640 | Каналы признаков YOLOv8s |
| --- | --- | --- | --- |
| P2 | 4 | 160x160 | 64 |
| P3 | 8 | 80x80 | 128 |
| P4 | 16 | 40x40 | 256 |
| P5 | 32 | 20x20 | 512 |

Backbone выдаёт стадии `(1,2,3,4)`, neck получает и возвращает четыре
масштаба, а head и prior generator используют `strides=[4,8,16,32]`.
Все четыре уровня участвуют в назначении положительных примеров и loss.

В P2-конфиге явно задано `model.bbox_head.head_module.cls_out_channels=128`:
две промежуточные свёртки каждой cls-ветви сохраняют ширину обычной YOLOv8s.
Это фактическое число каналов, без дополнительного умножения на `widen_factor`.
Ветви регрессии не меняются. Если параметр отсутствует или равен `None`,
сохраняется прежнее правило `max(in_channels[0], num_classes)`.

Датасет, число классов, нормализация, optimizer, расписание и пайплайны
наследуются из базового конфига. Thermal-аугментации основного пайплайна
сохраняются. Заключительный пайплайн после отключения Mosaic остаётся
таким же, как в базовом конфиге; thermal-аугментаций в нём нет.
Loss-веса также сохраняются из базового конфига.

При `--model-surgery 2` применяется тот же режим, что в обычном обучении:
FX surgery для backbone/neck и surgery v1 для head_module.
Исходный конфиг содержит SiLU, а после surgery используются ReLU.
Concat не заменяется на Add; Focus и grayscale-вход не добавляются.

## Маленькие объекты

P2 использует более плотную сетку, что даёт возможность лучше
локализовать маленькие объекты, занимающие лишь несколько пикселей
на более грубом P3. Это гипотеза для проверки на вашем датасете,
а не гарантия увеличения mAP.

При 640x640 число позиций детекции увеличивается с 8400 до 34000,
примерно в четыре раза. Это не означает ровно четырёхкратный рост
вычислений: стоимость также зависит от размеров и ширины свёрток.
Ожидайте больший расход памяти и вычислений; скорость на TIDL
нужно измерять отдельно. Сравнивайте mAP/recall маленьких объектов
и ложные срабатывания с обычной YOLOv8s при одинаковых условиях.

## Обучение

Запускайте из корня `mmyolo` (в Docker обычно `/mmyolo`):

```bash
CONFIG=configs/yolov8/yolov8_s_p2_syncbn_fast_8xb16-500e_coco.py
OUT=work_dirs/yolov8_s_p2_cls128_small_dataset_v3

python tools/train.py "$CONFIG" \
  --work-dir "$OUT" --model-surgery 2
```

Конфиг наследует текущий batch size базового конфига. Если памяти
не хватает, уменьшайте batch size и соответствующую настройку optimizer:

```bash
python tools/train.py "$CONFIG" \
  --work-dir "$OUT" --model-surgery 2 \
  --cfg-options train_dataloader.batch_size=8 \
  optim_wrapper.optimizer.batch_size_per_gpu=8
```

В новом конфиге заданы `load_from=None` и `resume=False`.
Старый трёхуровневый checkpoint нельзя напрямую использовать как
совместимые веса всей P2-модели: размеры neck/head и индексы ветвей
изменились. Перенос части весов требует отдельного сопоставления.
Приведённые команды запускают новое обучение, не автоматический fine-tuning.

Ранняя версия P2-конфига автоматически уменьшала cls-ветви до 64 каналов.
Её checkpoints несовместимы с исправленной шириной 128: запускайте отдельное
обучение в новом каталоге, не используйте `--resume` или старый `load_from`.
Для продолжения старого эксперимента либо его экспорта используйте сохранённый
конфиг из его `work_dir`. При использовании нового конфига прежнюю архитектуру
можно восстановить флагом
`--cfg-options model.bbox_head.head_module.cls_out_channels=64`
для `tools/train.py`. Для экспорта старых весов передавайте сохранённый
старый конфиг, а не обновлённый P2-конфиг: у экспортера нет `--cfg-options`.

## FP32 ONNX

После обучения выберите лучший checkpoint:

```bash
CONFIG=configs/yolov8/yolov8_s_p2_syncbn_fast_8xb16-500e_coco.py
OUT=work_dirs/yolov8_s_p2_cls128_small_dataset_v3
CHECKPOINT=$(find "$OUT" -maxdepth 1 \
  -name 'best_coco_bbox_mAP_epoch_*.pth' | sort -V | tail -n 1)

python projects/easydeploy/tools/export_onnx.py "$CONFIG" "$CHECKPOINT" \
  --model-only --model-surgery 2 --img-size 640 640 \
  --opset 11 --device cpu --work-dir "$OUT/onnx"
```

Квантование не выполняется. Вход: `(1,3,640,640)`.
По умолчанию model-only экспорт имеет четыре объединённых NCHW-выхода:

- `head_s4`: `(1,65,160,160)`.
- `head_s8`: `(1,65,80,80)`.
- `head_s16`: `(1,65,40,40)`.
- `head_s32`: `(1,65,20,20)`.

Для одного класса сначала идёт один cls-logit, затем 64 канала DFL.
При другом числе классов каналов будет `num_classes + 64`.
`--raw-output-format separate` даёт восемь отдельных выходов cls/bbox.
Постпроцесс должен учитывать четыре масштаба и шаги `[4,8,16,32]`;
постпроцесс, жёстко рассчитанный на три выхода, использовать нельзя.

## Проверки

Тест `tests/test_models/test_yolov8_p2.py` проверяет наследование
пайплайнов, признаки 160/80/40/20 при входе 640x640, шаг обучения
после surgery 2, четыре ONNX-выхода, prototxt и численное совпадение
PyTorch с ONNX Runtime. Полное обучение, качество и компиляция/скорость
на TIDL не входят в эти тесты.
